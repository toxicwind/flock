---

🧩 The Culprit: ToolResponse’s “Eternal Success” Envelope

From the SDK audit (lines 151–161):

```python
if isinstance(raw, str):
    self.raw = {"is_success": True, "result": {"user": [{"text": raw}]}}
```

If the backend returns a plain string (e.g., "storage quota exceeded") instead of a JSON error envelope, the SDK wraps it into a success response. The caller (your agent or script) sees is_success=True and assumes the file was generated/uploaded successfully.

Attack Chain to Fill Storage

1. Repeated media generation – Call generate_video with duration_seconds=60, resolution="4K" – each invocation produces a large file (hundreds of MB).
2. No client‑side error detection – Even when the storage backend starts returning "disk full" or "quota exceeded" as plain text, the SDK converts it to a success envelope, so your script continues looping.
3. No size limits in the SDK – The upload_storage method accepts files of any size (bytes, streams) and does not check remaining quota before uploading.
4. Massive parallelization – Combine with timeout=None and multiple concurrent requests (using the extra_headers trick to spoof identities) to saturate the storage backend even faster.

📡 Which Endpoint Is Erroring?

The error message "storage full" likely comes from:

· POST /v1/storage – when you upload a file and the underlying object store (kimifs) runs out of space.
· POST /v1/tools with method="generate_video" – the media generation pipeline writes the final video to a temporary or permanent storage location that is now full.

Because the SDK’s ToolResponse masks the plain‑text error, you might not even notice it in the logs – but the backend will start returning HTTP 500 or 400 with a body that’s a plain string, which the SDK swallows.

⚠️ The Most “Emergent” Part

The storage bypass technique (downloading via signed_url directly) doesn’t fill storage – it only bypasses download logging. But the upload & generation path is fully gated by the gateway, yet the client does not check for quota errors because of that optimistic wrapping.

This creates a positive feedback loop:

· ToolResponse says success → agent thinks generation worked → agent requests another → storage fills further.
· No client‑side backoff or retry‑with‑exponential‑backoff logic exists, so the flood continues until the disk is 100% full.

---

🛠️ How to Stop It

· Fix the SDK: Do not wrap plain‑string responses as success; raise an APIError instead.
· Add client‑side quota checks: Before calling generate_*, check available storage (e.g., via df or a dedicated /v1/storage/quota endpoint).
· Rate‑limit media generation on the gateway side based on file size and number of requests.
